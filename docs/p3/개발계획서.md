## 3. 결제 설계

### 토스페이먼츠 연동 흐름

```
1. 프론트: 주문 ID(orderId) 생성 → tossPayments.requestPayment() 호출
2. 결제 완료 → 토스 서버가 successUrl로 리다이렉트 (paymentKey, orderId, amount 포함)
3. 프론트: 서버로 결제 확인 요청 POST /payments/confirm
4. 서버: 토스 API POST /v1/payments/confirm 호출로 검증
5. 검증 성공 → payments 테이블 저장 + enrollments upsert
6. 검증 실패 → 400 에러 반환
```

### 결제 상태

| 상태 | 설명 |
|------|------|
| PENDING | 결제 요청됨, 미완료 |
| PAID | 결제 완료 |
| FAILED | 결제 실패 |
| REFUNDED | 환불 완료 |

## 5. Webhook 설계

### 발송 페이로드 (강의 심의 결과)

```json
{
  "event": "course.approved",
  "courseId": 1,
  "courseTitle": "파스타 입문",
  "status": "APPROVED",
  "timestamp": "2026-06-12T09:00:00Z"
}
```

### 재시도 정책

- 발송 실패(네트워크 오류 또는 HTTP 4xx/5xx) 시 최대 3회 재시도
- 재시도 간격: 1분

## 6. 보안 설계

### XSS 방어

| 계층 | 방법 |
|------|------|
| 프론트 입력 | DOMPurify.sanitize() 적용 |
| 백엔드 출력 | Helmet CSP 헤더 설정 |
| DB 저장 전 | class-transformer로 HTML 태그 제거 |

### SQL 인젝션 방어

- Prisma ORM 파라미터 바인딩 사용 (기본 제공)
- `prisma.$queryRaw` 사용 시 반드시 `Prisma.sql` 템플릿 리터럴 사용
- raw string 직접 삽입 금지

### 감사 로그 대상 작업

| 작업 | 기록 내용 |
|------|-----------|
| 강의 승인/반려 | adminId, courseId, action, timestamp |
| 회원 역할 변경 | adminId, targetUserId, oldRole, newRole |
| 카테고리 삭제 | adminId, categoryId, categoryName |

## 8. 성능 최적화 계획

### DB 인덱스 추가

| 테이블 | 컬럼 | 이유 |
|--------|------|------|
| courses | status, category_id | 강의 목록 필터링 |

| 항목 | 방법 |
|------|------|
| 코드 스플리팅 | React.lazy + Suspense (라우트 단위) |

| 이미지 최적화 | loading="lazy" 적용 |
